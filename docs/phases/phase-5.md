## 1. Scope

**In**

- **FinTS read-only sync** of the one rental account at a Sparkasse: a `bank_connection` per account (BLZ, FinTS URL, login name, the stored client state), a sync started from the account page or by a daily schedule, the pushTAN (decoupled) approval handled by polling, the booked camt documents the bank returns stored as one immutable ZIP (document source `bank_sync`, type `statement`) when they bring at least one new line (D127) and imported through the unchanged `import_statement` (phase 2 §7.2): same line hash, same dedup, same balance reconciliation, same `match_import` (§4). No write segment is ever reachable (non-goal: no write access to an account).
- **Scheduled sync**, daily, inside the bank's 180-day strong-authentication window, with an in-app card when the bank demands a new approval (§4.6); gated on the step 1 finding that Sparkasse serves reads TAN-free with a stored system id (python-fints issue #174 says yes once the system id is kept, §3).
- **Email-in** from the household's own Gmail account (Luis, 10 Nov 2026, §15 Q3): a plus-address token and a Gmail filter put forwarded mails under one label; the worker reads **only that label**, read-only, over IMAP every ten minutes with a Google app password; a mail is accepted only from a member's address, with Gmail's own authentication result, to the exact token address; attachments only, each becoming an `upload_document(source=email)`, a camt or CSV statement among them imported to the account its IBAN names; the body and the sender are never stored; nothing in the mailbox is changed (§5).
- **Reminders** computed on read from a catalogue in `rules/reminders.py` (as the document checklist is), shown as Zu prüfen cards and on the Übersicht, acknowledged through an append-only `reminder_ack`, and mailed as a daily digest through Scaleway Transactional Email with the kind of deadline and its date only (Luis, 10 Nov 2026, §15 Q2; §6). The Grundsteuer reminders follow the Bescheid once it exists (dates and amounts confirmed from its pre-fill into a `grundsteuer_schedule` tax input) and the statutory quarters before (D126).
- **Rule data 2027** for every per-year file, as a data PR when the Einkommensteuerreformgesetz 2027 and the Sozialversicherungs-Rechengrößen 2027 are in the Bundesgesetzblatt (§7; Luis, 10 Nov 2026, §15 Q6); until then the registries' latest-year fallbacks serve 2027 for projections, as phase 4 D81 and phase 4b D99 intended.

**Out**

- FinTS for any other account or bank (phase 6 adds the household's private accounts and will reuse `services/bank/fints.py`; the depot and crypto never go through FinTS); MT940 (`get_transactions` and its `mt-940` parser are not called: the app parses camt only, D33); PDF statements by FinTS (none exist); the aggregator (SaaS only); a TAN typed by hand (chipTAN, smsTAN): the sync supports the decoupled pushTAN only, since that is what the account uses, and refuses any other mechanism with `bank.tan_not_decoupled` (§4.4).
- Reading an email's body, inline text or links; replying to mail; moving, flagging or deleting any mail; a per-sender rule; any mail provider's inbound webhook (§5.1 says why); a separate mailbox or a second Gmail account (offered, declined: Luis, 10 Nov 2026).
- Web push notifications (§6.4: deferred, with what it would take), SMS, calendar feeds (an `.ics` export is a cheap later addition, noted in Q-O41).
- Reminders for things the app does not model: Einkommensteuer-Vorauszahlungen (phase 4b D95), the Kaution's return, insurance renewals, the Anlage SO deadline of phases 6–8.
- Document retention reminders: the auto-delete job of the retention policy is not built, so a "may be deleted on …" line would ask for an action nobody performs; it joins the retention job when that is built.
- Any 2027 figure before its enactment (§7): the files are written from the Bundesgesetzblatt, never from a bill.

```
→ lines_new > 0 → importing: upload_document(source=bank_sync, media_type=application/zip, original_filename="fints-<from>-<to>.zip")
          → import_statement(account, data) unchanged → if the file states no closing: declare HKSAL balance, balance_source=bank
→ done (lines_new, import status) | nothing_new | failed (error_code)
```

Every transition is an event on entity `account` (`bank.sync_started`, `bank.sync_approval_needed`, `bank.sync_completed` with `import_id`, `lines_total`, `lines_new`, `balance_source`, `balance_checked`, `reconciled`, `bank.sync_failed` with `error_code`); payloads carry counts and codes, never an amount, a name or the login. A failed run is retried by Procrastinate only for `bank.unreachable` (network, HTTP 5xx; `RetryLater` as `document_read` does, three attempts); every other failure waits for a person. A bank error with a code starting `9` (python-fints raises a generic `Exception` for it) is caught and recorded as `bank.refused` with the four-digit code only (never the bank's message text, which may quote the login name).

### 4.4 Errors (`bank.*`)

`bank.not_configured` (no PIN or product id in the environment), `bank.tan_not_decoupled`, `bank.approval_timeout`, `bank.sync_running`, `bank.rate_limited`, `bank.account_not_found`, `bank.state_rejected`, `bank.unreachable`, `bank.refused`, `bank.nothing_new` (an info code on the row, not a failure), `bank.balance_drift` (info card: HKSAL's booked balance differs from the last reconciled closing while nothing new arrived), `bank.unsupported_format` (the bank offers no camt format the parser reads: HICAZS lists none of `camt.052.001.02/08`, `camt.053.001.02/08`), `bank.window_invalid`, `bank.url_not_https`. D34's `statement.*` codes apply to the archive as to an upload.

### 4.5 Why the archive is the stored original, and when it is kept

The bytes the bank sends are the evidence (principle 6), and the vault, retention and the checklist already treat a statement document; a sync that stores lines without a document would be the first ledger input without an original. D127: a run whose every line is already known stores nothing (there is no new fact to keep an original for; the lines' originals are the earlier upload or sync), a run with a new line stores the whole ZIP, so every stored line has a stored original. Pending entries are not stored: they are not evidence of anything booked, and `transaction.is_pending` stays unused as phase 2 left it.

### 4.6 Schedule and the approval window

D120. The account page shows the last run, the next scheduled run, the estimated approval validity and a **Jetzt abrufen** button; a `needs_approval` row shows "In der S-pushTAN-App freigeben" with a countdown of the 5 minutes; a scheduled run's `needs_approval` card in Zu prüfen (`bank_approval_needed`) links to the same button. `bank.sync_stale` (§6.2) covers a connection that has not succeeded for 35 days.

### 4.7 Privacy and limits

The model never sees a sync: a camt ZIP is parsed by code (D33) and the lines go to matching exactly as uploaded ones (the LLM categorization step sees masked IBANs and one line at a time, phase 2 §8). The connection's UPD is stored without private data (`including_private=False`), so no account name or second account of the login is kept. One sync per account at a time; at most 4 manual starts per account per hour (`bank.rate_limited`), so a stuck phone cannot run up the bank's SCA counters.

## 5. Email-in (`services/inbound_mail.py`, `jobs/inbound_mail.py`, `rules/inbound_mail.py`)

### 5.1 Why IMAP polling of the household's own mailbox

D121. The alternatives were: Scaleway Transactional Email (no inbound, §3); an inbound-webhook provider with an EU region (Mailgun EU: works, but a US controller would hold every forwarded document before the app's tenant-data gate runs, and the webhook needs a public endpoint with signature checks on the API); Cloudflare Email Routing or a self-hosted SMTP (a US processor, or ops the household does not want); a new EU mailbox (mailbox.org, the draft's recommendation) or a separate Gmail account, both offered and declined. Reading the household's existing Gmail account adds no processor and no inbound endpoint: the worker opens an outbound IMAP-over-TLS connection every ten minutes, as it opens HTTPS to the bank and to the model, and the documents it reads are already in that mailbox.

### 5.2 Luis does

1. On the Google account: 2-Step Verification on (by a method other than security keys only; no Advanced Protection), then **create an app password** named "Hausbuch" (Security → 2-Step Verification → App passwords). This is the only credential; it is revoked on the same page.
2. Choose a **token**: 8 or more random characters, e.g. `k7f3q2xd`; the forwarding address is `<user>+<token>@gmail.com`.
3. A **Gmail filter**: "To: `<user>+<token>@gmail.com`" → apply the label `Hausbuch` (and, optionally, skip the inbox). Only mails to the token address get the label; the app reads nothing else.
4. Four values into Secret Manager and the container: `HAUSBUCH_INBOX_IMAP_USER` (the Gmail address), `HAUSBUCH_INBOX_IMAP_PASSWORD` (the app password), `HAUSBUCH_INBOX_ADDRESS` (the token address), `HAUSBUCH_INBOX_LABEL` (`Hausbuch`); `HAUSBUCH_INBOX_IMAP_HOST` defaults to `imap.gmail.com` and `HAUSBUCH_INBOX_AUTHSERV_ID` to `mx.google.com` (`deploy/scaleway.md` step 16).
5. **Test mail**: forward one PDF to the token address; step 4 records whether Gmail's `Authentication-Results` header is on the received copy (Q-O47).

The token address is shown on Einstellungen → Posteingang-Adresse with a copy button and three sentences: "Nur Anhänge werden übernommen; der Text der Mail wird nicht gespeichert. Die App liest nur das Label Hausbuch und verändert nichts im Postfach. Mieterunterlagen besser direkt hochladen, nicht weiterleiten."

### 5.3 The decision rule (`decide`, fixture `inbound_mail.yaml`)

Input `InboundMailFacts`: `from_address`, `recipients` (`To`, `Cc`, `Delivered-To`), `auth_results` (list of `(authserv_id, method, result, domain)` parsed from every `Authentication-Results` header), `parts` (list of `(index, filename | None, media_type, size_bytes, nested_rfc822: bool)`), `message_id_present`. Policy: `allowed_senders` (the members' emails), `token_address`, `authserv_id`, `media_types`, `max_attachments = 20`, `max_bytes = 25 MiB`. Output `MailDecision`: `accept: bool`, `code`, `attachments` (the part indexes to fetch, nested ones as `"2.1"`), `skipped` (parts of other types, counted only). The order of checks: recipient → sender → authentication → attachments present → limits; the first failure wins, and a rejected mail's parts are never fetched (the listing uses `BODYSTRUCTURE` and the header fields only).

### 5.4 Processing

Per accepted attachment, in one transaction per attachment (so one bad part does not lose the others): `detect_format` on the bytes; a statement with an `account_iban` matching exactly one non-owner account → `import_statement` (a CSV waits at `pending_balance` with its usual card); a statement matching no or several accounts → a plain `upload_document(source=email)` typed `statement` with the card `email.statement_unmatched`; anything else → `upload_document(source=email)` with the usual proposal job (`enqueue_document_read`), where the classifier's tenant-data gate applies (phase 2 §5.5). `inbound_mail` records the decision (one row per attempt; a message is final after an `accepted` or `rejected` row or three `failed` rows); `inbound_mail_attachment` links the documents and imports. Nothing is written to Gmail. The Zu prüfen card `email_received` ("3 Anhänge aus einer weitergeleiteten Mail übernommen") lists the documents for a day, computed on read from `inbound_mail` rows younger than 24 h; `email_failed` shows a message that failed three times (by time and code only).

### 5.5 What is never stored or logged, and what the mailbox sees

The sender, the subject, the body, any header, any address; the log line per poll carries counts and codes (`inbound_mail_polled accepted=1 rejected=0 failed=0`). The `Message-ID` is hashed (SHA-256, the IBAN pattern: a stored hash cannot be reversed to the id). A mail without a `Message-ID` is rejected (`email.no_message_id`): without it a re-delivery could not be told from a new mail. The mailbox sees only `EXAMINE` of the label, searches and `BODY.PEEK` fetches: no flag, label or folder changes, no deletion, no SMTP (D121's command whitelist test). A label folder that does not exist fails the poll with `email.label_missing` and a card, never a `CREATE`.

### 12.1 Step 0 readings and review decisions (10 Nov 2026)

Step 0 wrote these readings of points the spec left open into the fixture headers; the review judged them right, and they are the contract for steps 1–3:

- **Sync window (D120):** the first window starts the day after `opening_balance_on`, since phase 2's `reconcile` refuses a line on the anchor day (`statement.before_anchor`); the 14-day clamp uses the same bound. The 90-day flag is `end − start > 90` (91 flags, 90 does not).
- **Sync states (§9):** `SyncEvent.NEW_LINES` and `BankSync.connection_id` are added. Not yet pinned by any case and to be decided in step 1: running + worker lost, any event on a final row, queued + tan demanded. A manual start from the card restarts a scheduled run's `needs_approval` row; `bank.sync_running` refuses only while a run is `running` or `importing`.
- **The second write after the import (§4.3):** phase 2's `import_statement` takes no declared balance, and `declare_balances` writes `balance_source = user`; step 1 adds a sibling path that declares `bank` (D117). A failure between the import and `done` records `failed` with the `import_id` kept (§8).
- **Email-in (§5.3, D121):** the Message-ID check comes first (its hash is NOT NULL, so such a mail cannot be recorded); an SPF pass counts only for the From address's own domain; a forwarded `message/rfc822` is followed one level and never stored itself; the 25 MiB limit is on the encoded part; the accepted code is `email.accepted`.
- **Reminders (§6.2, §12):** `bank.sync_stale` is an info kind with an email lead, so `info_kind_never_mailed` means the info kinds without leads; a reminder is listed from 1 January of the previous year to today + 90 days; `rent_missing` needs at least one account that is not an owner account; the speculation end uses the latest rule set's `speculation_years`; `due_notifications` takes the recipients as a parameter; a lead that a later lead overtook is skipped, never sent late.
- **A failed reminder email is retried (D123 amended, orchestrator, 10 Nov 2026):** up to three attempts, one a day. `notification` keeps one row per attempt (`attempt` 1–3); a partial unique index allows one `sent` row per reminder, lead, channel and recipient. Before, one failure (a TEM 5xx) suppressed that lead's email entirely.
- **Login mask (D119):** `login_masked` keeps the first two and last two characters of a login of six or more, `***` below. If a Sparkasse login can be the account number, four of its digits reach an event; checked when step 1 connects.
- **The checklist fixture change of step 3 is authorised here (D126):** step 3 changes the existing cases of `tests/fixtures/phase1/document_checklist.yaml` and `checklist_phase3.yaml` that list a Grundsteuerbescheid item for the purchase year or without a due date (the first full year of ownership, due 15 January), and removes the `pending:` markers of the three new cases (§12 named two; step 0 added `grundsteuerbescheid_missing_on_15_jan_first_full_year`). `reminders.yaml`'s two `checklist.due` expectations already assume that change, so step 3 lands the checklist rule and the reminders rule together. ### 12.2 Step 4 review decisions (10 Nov 2026, PR #129)

The step 4 review (one round) found two real defects and three small ones; the fixes are in PR #129 (`1bdbfd8`, `b135e0e`, `6e738c4`, `c461f44`).

- **A poll that cannot go on shows a card** (the code first only logged it, against D121 and §5.5). Codes: `email.auth_rejected` (Google refused the app password: create a new one and paste it as the secret), `email.label_missing` (the label is gone or renamed: recreate it or correct its name; the poll never sends a `CREATE`), and the new `email.unreachable` (no connection to the IMAP server three polls in a row, about 30 minutes; the count lives in the worker process, so a container restart starts it again). Each change of outcome is one event on the workspace, `workspace.inbox_poll_failed {code}` or `workspace.inbox_poll_recovered {previous_code}`, codes only (D5), written only when the outcome changes, so the append-only log is not filled every ten minutes; no migration (the event table checks the entity type, which already allows `workspace`). The card, a seventh kind `email_inbox_failed` titled "Posteingang per E-Mail", is computed on read from the latest such event and disappears when a poll completes. A skipped poll (not exactly one workspace, `imaplib.Debug` set), a connection lost mid-poll and a database error stay log lines only.
- **A FETCH answered NO or unreadable is not a lost connection.** Gmail is known to refuse single messages; before, one such message stopped every poll and starved the label. For an attachment it now fails that mail's attempt (`email.failed`, retried, then the `email_failed` card). For a listing batch each UID is fetched alone, and one that still fails is counted as `unreadable` in the poll's log line and skipped; it has no Message-ID yet, so it is never recorded and gets no card (known gap). A SEARCH answered NO still ends the poll as a lost connection (once per poll, no attempt spent).
- **The accept limit follows `HAUSBUCH_MAX_UPLOAD_BYTES`** when that is below 25 MiB, so a part the upload would refuse is rejected as `email.too_large` before it is fetched.
- **The test double pins the header list**: a header fetch for any list other than `HEADER_FIELDS` is a violation.
- **Kept as is:** a retry after a partly failed attempt asks `proposal_for_upload` again for the parts already stored; only a proposal decided inside the ten minutes between attempts leads to a second read (one model call).
